# TURN 与 Python relay 操作延迟快速测量

2026-10-09，在同一台开发机、同一个可见 Firefox 会话和 1920×1080 Viewer 中，先后对旧 Python relay 与 TURN 各做 **50 次**操作。两轮之间按各自管理器正常停止并启动串流栈，因此 Isaac 曾重启；每轮页面用相同操作位置、画面区域、三秒间隔和两秒响应窗口。这是一份历史短测记录，不描述当前服务状态。

这次 50 次测量中，TURN 的 P50/P95、超时数、RTT 采样和解码停顿都优于 relay；两边也都出现了约一秒的长尾。初始十次快速试测曾给出不同印象，说明短时链路状态波动明显。结果支持继续用 TURN 做对照和优化，但还不能推断长期表现。

| 路径 | 菜单操作响应 | RTT 采样中位数 / 最大值 | 解码 FPS 采样中位数 | 无增长的解码采样间隔 |
|---|---|---|---:|---:|---:|
| Python relay | 48/50 响应；P50 130ms、P95 792ms、最大 1830ms；2 次两秒超时 | 35 / 2094ms | 60 | 4 |
| TURN/TCP | 50/50 响应；P50 93ms、P95 615ms、最大 1224ms；无超时 | 15 / 1298ms | 60 | 0 |

relay 有两个响应样本紧跟在超时之后，可能对应上一操作的迟到画面。因此主 P50/P95 根据 46 个未跟随超时的响应计算；响应总数仍如实记录 48/50。TURN 的 50 个响应都没有前一操作超时。两边 RTT 最大值都是 `getStats()` 采样值，可能重复或滞后。解码 FPS 是约一秒窗口内的帧计数差；四个无增长间隔提示可能停顿，但不等于按秒级数据精确量得的冻结时长。

## 测量方法

WebDriver 在同一个可见 Firefox 会话中点击远端 Isaac 的 Edit 菜单，每条路径各五十次，点击开始时间间隔约三秒。页面捕获可信的左键 `pointerdown`，以 `performance.now()` 记录输入；`requestVideoFrameCallback()` 中用 canvas 读取菜单区域，识别首次大幅变化并记录回调时间。计时不包含 SSH 或 WebDriver 命令传输时间。

这是**浏览器侧操作响应延迟估计**，不包含实体鼠标和显示器扫描输出的延迟。视频帧间隔、回调调度和区域变化阈值影响精度；没有将其称为精确网络单程延迟。没有桌面录像或复杂校准。

观察区域缩放到 160 像素宽；RGB 平均差异至少 10、差异超过 16 的像素比例至少 15% 时判定变化。两次试点的前后局部图像验证了区域选择。正式试验保留每次的输入前与响应后局部图像、事件和统计数据。

## 复现入口

在独立 `piper-stream-viewer` 仓库中使用已连接的可见 Firefox geckodriver 会话；先确认没有其他页面争用 Isaac 会话。这里的坐标只适用于本次页面布局：视频左上角为浏览器客户区 `(0,56)`，视频原始尺寸为 1920×1080。

```bash
python3 diagnostics/quick_latency.py \
  --port 4446 --session "$FIREFOX_SESSION_ID" \
  --point 45 68 --roi 35 30 220 170 \
  --count 50 --interval 3 \
  --output "$PRIVATE_RESULTS/turn-latency-quick-$(date +%Y%m%d-%H%M%S)"
```

`--point` 是浏览器客户区点击坐标，`--roi` 是原始视频中的 `x y width height`。更换窗口或操作时需相应调整，先用 `--count 2` 看局部图像是否确实发生变化。探针通过 WebDriver 临时注入，无需重新构建 Viewer；退出时停止采集并释放按键，保留当前浏览器连接和服务栈。

本轮原始证据保存在管理者仓库外的私有结果目录中。此前十次初始试测与 TURN 试点数据也留在同级目录。仓库仅保存脱敏结果和测量工具。

后续若继续测量，优先关注秒级停顿及其对应的 RTT/解码计数；与 relay 对照时使用相同操作和相同浏览器配置。
